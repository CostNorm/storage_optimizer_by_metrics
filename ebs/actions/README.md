# EBS 액션 실행기 (EBSActionExecutor)

이 모듈은 EBS 볼륨에 대한 실제 작업을 안전하게 수행하기 위한 클래스와 메서드를 제공합니다.

## 개요

`EBSActionExecutor` 클래스는 EBS 볼륨에 대한 다양한 작업(스냅샷 생성, 볼륨 분리/연결/삭제)을 안전하게 수행할 수 있는 기능을 제공합니다. 각 작업은 실행 전 사전 검증 단계를 거치며, 작업 완료를 확인하기 위한 대기 메커니즘도 포함하고 있습니다.

## 주요 기능

### 1. 스냅샷 관련 기능

- **스냅샷 생성**: `create_snapshot(volume_id, description, tags)`

  - EBS 볼륨의 스냅샷을 생성합니다.
  - 태그를 통한 메타데이터 설정을 지원합니다.
  - 생성 과정을 모니터링하고 완료를 대기합니다.

- **스냅샷 완료 대기**: `wait_for_snapshot_completion(snapshot_id, timeout_seconds, check_interval)`
  - 스냅샷 생성 과정이 완료될 때까지 기다립니다.
  - 타임아웃과 체크 간격 설정을 통해 대기 시간을 제어할 수 있습니다.

### 2. 볼륨 연결/분리 기능

- **볼륨 분리**: `detach_volume(volume_id, force)`

  - EBS 볼륨을 EC2 인스턴스에서 안전하게 분리합니다.
  - 루트 볼륨 여부를 확인하는 안전 장치가 포함되어 있습니다.

- **볼륨 연결**: `attach_volume(volume_id, instance_id, device)`

  - EBS 볼륨을 EC2 인스턴스에 연결합니다.
  - 볼륨과 인스턴스 상태를 사전에 확인합니다.

- **볼륨 상태 대기**: `wait_for_volume_detachment`, `wait_for_volume_attachment`
  - 볼륨의 분리/연결 작업이 완료될 때까지 기다립니다.
  - 진행 상황을 로그로 기록합니다.

### 3. 볼륨 삭제 기능

- **볼륨 삭제**: `delete_volume(volume_id)`

  - EBS 볼륨을 영구적으로 삭제합니다.
  - 볼륨이 연결되어 있지 않은지 사전에 확인합니다.

- **볼륨 삭제 대기**: `wait_for_volume_deletion(volume_id, timeout_seconds, check_interval)`
  - 볼륨이 완전히 삭제될 때까지 기다립니다.
  - 예외 처리를 통해 삭제 완료 여부를 확인합니다.

### 4. 안전 장치 기능

- **볼륨 안전성 확인**: `_is_volume_safe_to_detach(volume_id, instance_id)`
  - 볼륨이 루트 볼륨인지 확인하여 분리 가능 여부를 판단합니다.
  - 인스턴스 정보를 조회하여 루트 디바이스 이름과 비교합니다.

## EBS 메트릭에 따른 의사결정 로직

EBS 볼륨 최적화는 다양한 CloudWatch 메트릭을 기반으로 의사결정을 수행합니다. 이러한 메트릭 분석을 통해 유휴 상태 볼륨과 과대 프로비저닝된 볼륨을 식별하고 적절한 조치를 취합니다.

### 1. 유휴 상태 볼륨 감지 로직

유휴 상태 볼륨은 사용률이 매우 낮은 볼륨을 의미하며, 다음 메트릭을 기준으로 판단합니다:

#### 주요 판단 메트릭:

- **VolumeIdleTime**: 볼륨이 유휴 상태로 보내는 시간 (분당 초 단위로 측정)

  - **변환 로직**: 측정값(초) / 60 \* 100 = 유휴 시간 백분율
  - **임계값**: 95% 이상이면 유휴 상태로 간주
  - **예시**: 59.87초/분 → 99.78% 유휴 상태

- **VolumeReadOps / VolumeWriteOps**: 읽기/쓰기 작업 수

  - **임계값**: 일 평균 합계 작업 수 10 미만 (현재는 판단에서 제외됨)

- **VolumeReadBytes / VolumeWriteBytes**: 데이터 처리량

  - **임계값**: 일 평균 총 처리량 5MB 미만 (현재는 판단에서 제외됨)

- **BurstBalance**: 버스트 가능한 볼륨(gp2/st1/sc1)의 성능 크레딧 잔액
  - **임계값**: 90% 이상이면 거의 사용하지 않는 것으로 간주

#### 의사결정 흐름:

1. 볼륨의 VolumeIdleTime이 95% 이상인지 확인
2. (선택적) 일 평균 IO 작업 수 확인
3. (선택적) 일 평균 처리량 확인
4. 볼륨 유형에 따라 BurstBalance 확인
5. 조건 충족 시 다음 작업 중 하나 권장:
   - `snapshot_and_delete`: 스냅샷 생성 후 볼륨 삭제
   - `snapshot_only`: 스냅샷만 생성하여 백업
   - `change_type`: 비용 효율적인 볼륨 유형으로 변경

### 2. 과대 프로비저닝된 볼륨 감지 로직

과대 프로비저닝된 볼륨은 할당된 용량에 비해 실제 사용량이 현저히 적은 볼륨을 의미합니다.

#### 주요 판단 메트릭:

- **disk_used_percent**: CloudWatch 에이전트를 통해 수집된 파일시스템 사용률

  - **임계값**: 20% 미만이 장기간(6개월 이상) 지속되면 과대 프로비저닝으로 간주

- **볼륨 크기와 IOPS 사용 패턴**: 프로비저닝된 IOPS와 실제 사용된 IOPS 비교
  - **수집 방법**: `VolumeReadOps`, `VolumeWriteOps` 메트릭을 분석
  - **임계값**: 프로비저닝된 IOPS의 20% 미만을 지속적으로 사용

#### 의사결정 흐름:

1. CloudWatch 에이전트 측정 데이터 또는 SSM을 통한 디스크 사용률 확인
2. 디스크 사용률이 20% 미만인지 확인
3. 사용 패턴이 장기간(6개월) 동안 지속되는지 확인
4. 조건 충족 시 다음 작업 중 하나 권장:
   - `resize`: 적절한 크기로 볼륨 축소
   - `migrate`: 더 저렴한 스토리지 계층으로 데이터 이전

## 조치 실행 결정 로직

분석 결과를 바탕으로 다음과 같은 우선순위로 액션을 결정합니다:

### 유휴 볼륨 조치 결정:

1. **중요도 평가**: 볼륨 태그, 연결된 인스턴스 등을 검토하여 중요도 확인
2. **리스크 평가**:
   - 루트 볼륨이면 조치 수행하지 않음 (`_is_volume_safe_to_detach` 메서드로 확인)
   - 최근 연결/분리 이력 검토하여 활발히 사용 중인지 확인
3. **볼륨 유형 분석**:
   - io1/io2 볼륨은 비용이 높으므로 우선적으로 조치
   - gp2 볼륨은 gp3로 마이그레이션 권장 (성능은 동등하나 비용 절감)

### 과대 프로비저닝 볼륨 조치 결정:

1. **비용 영향 평가**: 현재 크기와 적정 크기의 비용 차이 계산
2. **성능 요구사항 분석**:
   - 최대 IOPS 사용량 검토
   - 볼륨 처리량 패턴 분석
3. **최적 크기 추천**: 현재 사용량 + 20% 버퍼를 적정 크기로 권장

## 조치 실행 시 안전장치

권장된 조치를 실행할 때 다음과 같은 안전장치가 적용됩니다:

1. **자동 스냅샷 생성**: 모든 수정/삭제 작업 전 스냅샷 자동 생성
2. **루트 볼륨 보호**: 루트 볼륨은 절대 분리하거나 삭제되지 않도록 방지
3. **인스턴스 상태 확인**: 실행 중인 인스턴스의 볼륨만 분리 가능
4. **조치 단계적 실행**: 위험한 작업은 여러 단계에 걸쳐 검증하며 실행
5. **타임아웃 관리**: 모든 대기 작업에 타임아웃 설정하여 무한 대기 방지
