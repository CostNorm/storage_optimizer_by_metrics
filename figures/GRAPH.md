# AWS Service Cost Optimization Comparison Graph Explanation

This document explains the stacked bar chart generated by `graph.py`, which visualizes the potential cost savings for various AWS services based on specific optimization scenarios detailed in the main report.

## Graph Overview

- **Purpose:** To compare the estimated monthly costs of selected AWS services _before_ and _after_ applying specific cost optimization strategies.
- **Type:** Stacked Bar Chart. Each bar represents a single optimization scenario for a specific AWS service.
- **X-axis:** Shows the AWS service and the specific optimization scenario applied.
- **Y-axis:** Represents the Monthly Cost in USD.

## Bar Composition

Each bar is divided into two segments:

1.  **After Cost (Light Coral):** The bottom segment represents the estimated monthly cost _after_ the optimization strategy has been implemented.
2.  **Savings (Sky Blue):** The top segment, stacked on the 'After Cost', represents the estimated monthly cost savings achieved through the optimization. (`Savings = Before Cost - After Cost`).

The **total height** of each bar represents the original estimated monthly cost _before_ optimization (`Before Cost = After Cost + Savings`).

## Labels

- **Top of Bar:** A text label is placed above each bar indicating:
  - The total 'Before Cost' in USD (e.g., `$50.00`).
  - The percentage of cost saved through optimization (e.g., `(20.0% saved)`).
- **Legend:** Explains the colors used for the 'After Cost' and 'Savings' segments.
- **X-axis Labels:** Clearly state the AWS service and the specific scenario being compared (e.g., `EBS\n(gp2 → gp3 Migration (500 GB))`).

## Scenarios Included

The graph visualizes the following specific scenarios, highlighting significant cost reduction opportunities:

1.  **EBS: gp2 → gp3 Migration (500 GB)**
    - **Context:** Migrating a 500 GB General Purpose SSD `gp2` volume to the newer `gp3` type.
    - **Rationale:** `gp3` volumes offer comparable or better baseline performance (IOPS and throughput) independent of volume size, often at a lower storage cost (up to 20% less) compared to `gp2`, whose performance scales with size. This makes `gp3` particularly cost-effective for volumes needing consistent performance without requiring extremely large capacity. (Ref: Report Section 2.3.1, 2.3.2)
2.  **EFS: Lifecycle Management (Standard → Archive, 1 TB)**
    - **Context:** Applying an EFS Lifecycle policy to a 1 TB file system where only 10% of data is accessed daily, and the remaining 90% is accessed less frequently (e.g., once every 90 days).
    - **Rationale:** EFS Lifecycle Management automatically transitions infrequently accessed files to lower-cost storage classes (Infrequent Access or Archive). Archive offers the lowest storage cost for long-term retention, making it ideal for data that is rarely needed but must be kept. This scenario shows significant savings by moving the bulk of the data to the Archive tier. (Ref: Report Section 2.6.1, 2.6.2, Table 2.6.4)
3.  **RDS: Instance Downsizing (m5.xlarge → m5.large)**
    - **Context:** An RDS instance running on `db.m5.xlarge` is identified as over-provisioned based on metrics like low average `CPUUtilization` (<30%) and high average `FreeableMemory` (>70%) over an extended period (e.g., 3 months).
    - **Rationale:** Downsizing the instance to a smaller type (`db.m5.large` in this case) aligns the allocated resources (CPU, memory) more closely with the actual workload demand, thereby reducing instance compute costs significantly without impacting necessary performance. (Ref: Report Section 2.10.1, 2.10.2, Table 2.10.5)
4.  **S3: Lifecycle Policy (Standard → Deep Archive, 1 TB)**
    - **Context:** Implementing an S3 Lifecycle policy for 1 TB of data intended for long-term archival, transitioning it from S3 Standard through intermediate tiers (like One Zone-IA in the example) eventually to S3 Glacier Deep Archive.
    - **Rationale:** S3 Glacier Deep Archive provides the lowest-cost cloud storage, designed for data accessed perhaps once or twice a year. Automating the transition using lifecycle policies ensures data is moved to the most cost-effective tier based on its age or access patterns, ideal for compliance, backups, or data archiving needs with substantial cost savings for storage. (Ref: Report Section 2.15.1, Table 2.15.4)

_(Note: All cost estimations are based on the us-east-1 region pricing as of November 2024, according to the provided report data.)_

# AWS 서비스 비용 최적화 비교 그래프 설명

이 문서는 `graph.py` 스크립트에 의해 생성된 누적 막대 그래프에 대해 설명합니다. 이 그래프는 메인 보고서에 상세히 기술된 특정 최적화 시나리오를 기반으로 다양한 AWS 서비스의 잠재적 비용 절감 효과를 시각화합니다.

## 그래프 개요

- **목적:** 특정 비용 최적화 전략을 적용하기 *전*과 *후*의 선택된 AWS 서비스 월별 예상 비용 비교.
- **유형:** 누적 막대 그래프 (Stacked Bar Chart). 각 막대는 특정 AWS 서비스에 대한 단일 최적화 시나리오를 나타냅니다.
- **X축:** AWS 서비스와 적용된 특정 최적화 시나리오를 보여줍니다.
- **Y축:** 월별 비용 (USD)을 나타냅니다.

## 막대 구성

각 막대는 두 부분으로 나뉩니다:

1.  **최적화 후 비용 (After Cost - 연한 산호색):** 하단 부분은 최적화 전략이 구현된 *후*의 예상 월별 비용을 나타냅니다.
2.  **절감액 (Savings - 하늘색):** '최적화 후 비용' 위에 쌓인 상단 부분은 최적화를 통해 달성된 예상 월별 비용 절감액을 나타냅니다. (`절감액 = 최적화 전 비용 - 최적화 후 비용`).

각 막대의 **전체 높이**는 최적화 *전*의 원래 예상 월별 비용을 나타냅니다 (`최적화 전 비용 = 최적화 후 비용 + 절감액`).

## 레이블

- **막대 상단:** 각 막대 위에는 다음을 나타내는 텍스트 레이블이 표시됩니다:
  - 총 '최적화 전 비용' (USD) (예: `$50.00`).
  - 최적화를 통해 절감된 비용 비율 (예: `(20.0% saved)`).
- **범례 (Legend):** '최적화 후 비용'과 '절감액' 부분에 사용된 색상을 설명합니다.
- **X축 레이블:** 비교 대상인 AWS 서비스와 특정 시나리오를 명확하게 표시합니다 (예: `EBS\n(gp2 → gp3 Migration (500 GB))`).

## 포함된 시나리오

그래프는 상당한 비용 절감 기회를 강조하는 다음 특정 시나리오를 시각화합니다:

1.  **EBS: gp2 → gp3 마이그레이션 (500 GB)**
    - **배경:** 500 GB 범용 SSD `gp2` 볼륨을 최신 `gp3` 유형으로 마이그레이션하는 시나리오입니다.
    - **근거:** `gp3` 볼륨은 볼륨 크기와 관계없이 유사하거나 더 나은 기본 성능(IOPS 및 처리량)을 제공하며, 성능이 크기에 비례하는 `gp2`에 비해 종종 더 낮은 스토리지 비용(최대 20% 저렴)을 제공합니다. 이는 매우 큰 용량이 필요하지 않으면서 일관된 성능이 필요한 볼륨에 대해 `gp3`를 특히 비용 효율적으로 만듭니다. (참조: 보고서 섹션 2.3.1, 2.3.2)
2.  **EFS: 수명 주기 관리 (Standard → Archive, 1 TB)**
    - **배경:** 1 TB 파일 시스템에 EFS 수명 주기 정책을 적용하는 시나리오입니다. 이 데이터의 10%만 매일 액세스되고 나머지 90%는 접근 빈도가 낮습니다(예: 90일에 한 번).
    - **근거:** EFS 수명 주기 관리는 접근 빈도가 낮은 파일을 저렴한 스토리지 클래스(Infrequent Access 또는 Archive)로 자동으로 전환합니다. Archive는 장기 보존을 위한 가장 저렴한 스토리지 비용을 제공하므로, 거의 필요하지 않지만 보관해야 하는 데이터에 이상적입니다. 이 시나리오는 데이터의 대부분을 Archive 티어로 이동함으로써 상당한 절감 효과를 보여줍니다. (참조: 보고서 섹션 2.6.1, 2.6.2, 표 2.6.4)
3.  **RDS: 인스턴스 다운사이징 (m5.xlarge → m5.large)**
    - **배경:** `db.m5.xlarge`에서 실행 중인 RDS 인스턴스가 장기간(예: 3개월) 동안 낮은 평균 `CPUUtilization`(<30%) 및 높은 평균 `FreeableMemory`(>70%)와 같은 지표를 기반으로 과다 프로비저닝된 것으로 식별되었습니다.
    - **근거:** 인스턴스를 더 작은 유형(`db.m5.large`)으로 다운사이징하면 할당된 리소스(CPU, 메모리)를 실제 워크로드 요구 사항에 더 가깝게 조정하여 필요한 성능에 영향을 주지 않으면서 인스턴스 컴퓨팅 비용을 크게 절감할 수 있습니다. (참조: 보고서 섹션 2.10.1, 2.10.2, 표 2.10.5)
4.  **S3: 수명 주기 정책 (Standard → Deep Archive, 1 TB)**
    - **배경:** 장기 아카이브 목적의 1 TB 데이터에 대해 S3 수명 주기 정책을 구현하여 S3 Standard에서 중간 티어(예시의 One Zone-IA 등)를 거쳐 최종적으로 S3 Glacier Deep Archive로 전환하는 시나리오입니다.
    - **근거:** S3 Glacier Deep Archive는 1년에 한두 번 정도 액세스하는 데이터를 위해 설계된 가장 저렴한 클라우드 스토리지를 제공합니다. 수명 주기 정책을 사용하여 전환을 자동화하면 데이터의 보관 기간이나 접근 패턴에 따라 가장 비용 효율적인 티어로 데이터가 이동되도록 보장하며, 규정 준수, 백업 또는 데이터 아카이브 요구 사항에 이상적이며 스토리지 비용을 대폭 절감할 수 있습니다. (참조: 보고서 섹션 2.15.1, 표 2.15.4)

_(참고: 모든 비용 추정치는 제공된 보고서 데이터를 기준으로 하며, 2024년 11월 us-east-1 리전 요금을 기반으로 합니다.)_
